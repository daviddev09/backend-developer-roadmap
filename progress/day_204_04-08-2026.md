# День 204 (04.08.2026): Стратегии кеширования на уровне приложения
## Теория:
* Паттерн Cache-Aside (Ленивое кеширование): самая популярная стратегия. Приложение сначала ищет данные в кеше (Cache Hit). Если их нет (Cache Miss), оно идет в базу данных, сохраняет результат в кеш и отдает пользователю.
* Проблема инвалидации кеша: как и когда нужно удалять устаревшие данные из Redis, если они изменились в основной базе данных (Event-driven инвалидация против простого TTL).
* Кеширование JSON: как правильно сериализовать сложные Python-словари и списки в строку перед записью в Redis (с помощью модуля json) и десериализовать при чтении.
* Опасности кеширования: что такое Cache Stampede (пробой кеша) и почему нельзя кешировать абсолютно всё (переполнение оперативной памяти).

## Конспект изученных материалов
### 1. Паттерн Cache-Aside
* **Cache-Aside (он же Lazy Loading)** - это самая популярная и универсальная стратегия кэширования для приложений с преобладанием операций чтения (Read-Heavy).
* **Суть паттерна:** приложение выступает посредником между Redis и основной базой данных. База данных и кэш прямо друг с другом не общаются.
### 2. Проблема инвалидации кэша
* Когда данные обновляются в базе данных, кэш моментально становится устаревшим (stale data). Если пользователь изменит свое имя в профиле, а кэш останется прежним, система будет показывать ему старые данные. **Есть две концепции борьбы с этим:**
    1. **Инвалидация по времени (TTL - Time To Live):** Мы задаем жесткое время жизни ключа (например, setex(..., 300, ...)).
        * Плюсы: Прост в реализации. Не требует сложной логики очистки.
        * Минусы: Возникает "окно рассинхронизации". Если данные изменились на 1-й секунде, а TTL у ключа 300 секунд, пользователь будет 5 минут видеть старые данные.
    2. **Событийная инвалидация (Event-Driven / Cache Eviction):** Мы явно стираем или обновляем ключ в Redis сразу в момент, когда происходят операции UPDATE, DELETE или INSERT в основной базе.
        * Плюсы: Данные всегда актуальны.
        * Минусы: Сложность поддержки. Если с пользователем связаны 10 разных ключей кэша (user:1:orders, user:1:stats и т.д.), тебе придется отслеживать и удалять их все.
### 3. Кеширование JSON и работа со сложными структурами
* Redis умеет хранить строки, бинарные данные и числа. Сложные объекты Python (словари, списки, экземпляры Pydantic-моделей) нельзя просто так передать в redis.set(). Сначала их нужно сериализовать в строку, а при чтении — десериализовать. Стандартный формат для этого - JSON, но, можно использовать и Pydantic модели
