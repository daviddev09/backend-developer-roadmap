# День 197 (02.08.2026): Краевые случаи (Edge Cases), валидация и обработка ошибок
## Теория:
* Негативное тестирование (Negative Testing): проверка того, как система справляется с некорректным вводом (сломанный JSON, неправильные типы данных, слишком длинные строки).
* Специфичные статус-коды HTTP: когда API должно возвращать 400 Bad Request (ошибка бизнес-логики), 404 Not Found (ресурс не найден), 409 Conflict (дублирование данных) и 422 Unprocessable Entity (ошибка валидации схемы).
* Важность тестирования ошибок 500: как убедиться, что внутренние сбои (например, разрыв связи с БД) не "сливают" пользователю чувствительную информацию (stack trace), а отдают корректный JSON с извинениями.
## Практика:
* Напиши тест, отправляющий в эндпоинт создания ресурса невалидный JSON (например, строка вместо числа или отсутствие обязательного поля), и проверь, что API возвращает 422 Unprocessable Entity с детальным описанием ошибки в теле ответа.
* Напиши тест на запрос несуществующего ресурса (например, GET /api/items/999999) и проверь, что возвращается строгий 404 Not Found, а не 500-я ошибка от базы данных.
* Напиши тест на нарушение бизнес-логики (например, попытка купить товар, если на балансе юзера недостаточно средств), ожидающий 400 Bad Request.
* Проверь покрытие кода интеграционными тестами (pytest --cov) и убедись, что блоки except в твоих контроллерах тоже выполняются во время прогона.

## Конспект изученных материалов
### 1. Негативное тестирование и краевые случаи
* **Краевые случаи** это ситауции, которые находятся на границе допустимых значений.
* **Негативное тестирование** проверяет работу поведения системы, когда в неё летит откровенный мусор.
### 2. Специфичные статус коды
* **422 Unprocessable Entity:** ошибка формата данных. Запрос понятен, но данные не прошли проверку схемы.
* **404 Not Found:** ресурс, к которому обращаются, физически отсутствует в базе данных.
* **409 Conflict:** данные валидны, но их сохранение нарушает уникальность записей в БД.
* **400 Bad Request:** Данные валидны, но нарушена бизнес-логика.
### 3. Важность тестирования ошибок 500
* Ошибки **500 Internal Server Error** случаются, когда падает сервер. Их опасность заключается в том что, фреймворк по умолчанию могут вернуть клиенту Stack Tree - полный путь ошибки с указанием строк кода, версий библиотек, а иногда и паролей от БД, которые попали в переменные. Это критическая уязвимость.
* Тесты должны гарантировать, что при внутреннем сбое приложение возвращает стандартизированный, безопасный JSON, ничего не рассказывая о внутренностях.
