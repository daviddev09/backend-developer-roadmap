# День 179 (27.07.2026): Разделение окружений (Dev, Test, Prod)
## Теория:
* Понятие жизненного цикла приложения: почему локальная разработка (Development), тестирование (Testing) и боевой сервер (Production) должны использовать разные базы данных и разные ключи.
* Как управлять разными окружениями с помощью переменной ENVIRONMENT или APP_ENV.
* Подходы к хранению настроек: использование префиксов (например, DEV_DB_URL и PROD_DB_URL) или использование разных файлов (например, .env.test).
* Переопределение переменных: как переменные, переданные прямо в терминале при запуске программы, перекрывают те, что записаны в файле .env.
## Практика:
* В своем классе конфигурации (из Дня 178) добавь переменную APP_ENV со значением по умолчанию development.
* Напиши логику в коде: если APP_ENV равно development, программа выводит "Подключение к локальной БД", если production — "Подключение к боевой БД".
* Запусти программу обычным способом — убедись, что сработал режим разработки.
* Запусти программу, передав переменную прямо в консоли (например: APP_ENV=production python main.py для Mac/Linux) и убедись, что поведение изменилось без редактирования кода.

## Конспект изученных материалов
### 1. Жизненный цикл приложения
* Когда пишется код, он проходит через несколько окружений, прежде чем попасть к реальным пользователям. Если локальный код будет смотреть в ту же БД что и рабочий сервер, рано или поздно можно случайно удалить реальные данные пользователей. Чтобы этого не произошло, проект делят минимум на три изолированных мира: Development, Testing, Production
### 2. Как управлять разными окружениями
* Чтобы код понимал где именно он сейчас запущен (локально или на сервере), используют всего одну переменную окружения - APP_ENV и в зависимости от значения этой переменной, программа принимает решение, какие именно настройки загружать.
###  3. Подходы к хранению настроек
* Чтобы передавать разные ключи для разных окружений, есть два основных подхода.
* **Подход А:** Использование префиксов
    * Все секретные ключи хранятся в одном файле .env но добавляются к ним префиксы, например: DEV_DB_URL, PROD_DB_URL
    * **Проьлема:** Локальный .env содержит пароли от боевой базы. Если ноут украдут или случайно файл сольется в сеть, хакеры получат доступ к Production.
* **Подход Б:** Использование разных файлов
    * Создается несколько файлов .env под каждое окружение. В коде пишется логика, которая читает нужный файл в зависимости от APP_ENV.
    * **.env.development** (для работы локально)
    * **.env.test** (для автотестов)
    * **.env.production** (лежит только на боевом сервере)
### 4. Переопределение переменных
* Библиотеки вроде python-dotenv или pydantic-settings работают по очень важному правилу: системные переменные окружения ОС всегда важнее тех, что записаны в файле .env. Файл .env - это просто удобный способ симудировать системные переменные, чтобы не вводить их каждый раз руками. Но если переменная передана при запуске, файл .env будет проигнорирован.
