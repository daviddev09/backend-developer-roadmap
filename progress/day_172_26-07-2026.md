# День 172 (26.07.2026): Структура Workflow и использование готовых Action'ов
## Теория:
* Глубокое погружение в синтаксис YAML для GitHub Actions: иерархия name, on, jobs, steps.
* Использование чужих наработок: ключевое слово uses. Вместо того чтобы писать десятки команд терминала, можно использовать готовые экшены из GitHub Marketplace.
* Главный экшен actions/checkout@v4: почему виртуальный сервер изначально пустой и как этот экшен скачивает твой код на раннер.
* Подготовка окружения: экшены вроде actions/setup-python@v5 или actions/setup-node@v4 для быстрой установки нужной версии языка программирования.
* Многошаговые задачи: как передавать результаты от одного шага (step) к другому и использовать ключевое слово run для запуска скриптов.
## Практика:
* Создай новый файл linter.yml для автоматической проверки чистоты кода.
* Настрой триггер так, чтобы процесс запускался не на любой push, а только на пуши в ветку main.
* В шагах (steps) используй checkout, затем установи Python с помощью setup-python.
* В следующем шаге напиши run: pip install flake8 (или ruff).
* В последнем шаге запусти линтер для проверки твоего кода. Запушь изменения и посмотри результаты во вкладке Actions.

## Конспект изученных материалов
### 1. Глубокое погружение в синтаксис YAML
* Файлы конфигурации GitHub Actions строятся на иерархии формата YAML. Файлы формата YAML очень чувствительны к отступам (используются пробелы вместо Табов).
* **Иерархия конфигурации GitHub Actions:**
    * **name:** Это название рабочего процесса, которое будет светится во вкладке Actions на GitHub.
    * **on:** Блок триггер. Он срабатывает при определённых событиях (Пуш в ветку main или PR и т.д.)
    * **jobs:** Блок задач. Один файл конфигурации может содержать несколько задач. И все эти задачи выполняются параллельно на разных виртуальных серверах.
    * **steps:** Блок шагов внутри конкретной Job (задачи). Здесь описываются каждые шаги внутри задачи. Шаги отличаются от Job тем что они последовательны, запускаются на одном виртуальном сервере и второй шаг зависит от первого, третий от второго, и если какой-то упадет дальнейшие шаги не запустятся.
### 2. Использование чужих наработок.
* Использовать чужие наработки можно с помощью ключевого слова **uses**. Экшены это скрипты, которые написаны другими разработчиками и которые упакованы в удобные блоки. Символ **@v...** в конце указывает на версию экшена.
### 3. Главный экшен
* Чтобы начать работу, экшен *actions/checkout@v4* скачивает код из текущего репозитория на новый раннер. Под капотом он делает *git clone* репозитория в рабочую директорию виртуальной машины.
### 4. Подготовка окружения
* Когда репозиторий скачан на сервер, чистая Ubuntu может не иметь нужные инструменты для запуска CI. Для этого используются специальные экшены для настройки окружения, например: *actions/setup-python@v5* для быстрой установки нужной версии языка программирования. И вместо того чтобы писать длинные bash команды, настраивать пути, экшен делает это сам.
### 5. Многошаговые задачи 
* Многошаговые задачи пишутся в блоке: **run:** с помощью символа **|**(pipe). Pipe позволяет писать многострочный скрипт.
