# День 173 (26.07.2026): Запуск автоматических тестов на Pull Request (CI)
## Теория:
* Суть непрерывной интеграции: почему тесты должны запускаться именно в момент создания или обновления Pull Request'а, до того, как код попадет в main.
* Триггер pull_request: настройка workflow на реагирование на PR.
* Воспроизведение локальной среды: как правильно устанавливать зависимости проекта на раннере (через requirements.txt, Pipfile или poetry).
* Понятие Exit Code (код возврата): как GitHub Actions понимает, что тест провалился. (Если программа завершается с кодом 0 — зелёная галочка, если отличным от нуля — красный крестик и остановка процесса).
## Практика:
* Напиши 1–2 простых автоматических теста для своего проекта (например, используя pytest).
* Создай файл tests.yml. Настрой триггер на on: [pull_request].
* Опиши шаги: checkout кода -> установка нужной версии языка -> установка зависимостей из файла -> запуск тестов (например, run: pytest).
* Создай новую ветку, специально сломай код так, чтобы тест не прошел, и открой PR на GitHub.
* Убедись, что GitHub Actions показал ошибку тестирования. Исправь код в локальной ветке, запушь снова и дождись зеленой галочки в PR.

## Конспект изученных материалов
### 1. Суть непрерывной интеграции (CI)
* **Своими словами:** Суть в том что в профессиональной разработке никто не пушит изменения напрямую в main. main это ветка в которую всегда должен попадать чистый работающий код. Вместо того чтобы пушить изменения напрямую в main, нужно открывать Pull Request и писать для него CI конфигурацию. Проверка должна начинаться до слияния PR, ведь если Pull Request уже слит и оказалось что была ошибка, чистота main испортится, и поэтому сначала открывается Pull Request -> проводятся тесты -> и только если тесты зелёные -> Merge Pull Request
### 2. Триггер pull_request
* **Своими словами:** Чтобы GitHub понимал когда что нужно запускать тесты только во время открытия Pull Request, а не при каждом push, в блок **on:** в файле конфигурации YAML добавляется триггер: **pull_request:**
### 3. Воспроизведение среды
* Когда запускаются тесты, GitHub выделяет чистый сервер с чистой ВМ. Чтобы запустились проекты туда нужно установить необходимые зависимости. Они устанавливаются после того как был установлен интерпретатор Python на тот сервер, в блоке **run:** здесь устанавливаются все зависимости проекта, например: **run:** *pip install -r requirements.txt*
### 4. Понятие Exit Code
* **Своими словами:** в Linux каждая программа имеет код завершения. Если процесс выполнения программы завершился успешно, он возвращает код **0**. Если случилась ошибка оно возвращает любой код кроме нуля. Но GitHub Action ничего не знает о том как завершился тесты pytest или что-то ещё, он лишь смотрит на этот код. Если код нулевой значит тесты прошли успешно, если код не нулевой он останавливает тесты и возвращает ошибку и указывает на неё.
