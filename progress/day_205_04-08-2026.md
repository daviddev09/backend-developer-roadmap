# День 205 (04.08.2026): Продвинутые структуры данных и Pub/Sub в Redis
## Теория:
* Использование хешей (Redis Hashes): почему хранение объекта пользователя как структуры HSET часто эффективнее, чем сохранение огромной JSON-строки, если тебе нужно менять только одно поле (например, возраст или баланс).
* Списки (Lists) для очередей: как команды LPUSH и RPOP превращают Redis в простую, но быструю очередь задач.
* Множества (Sets) для уникальности: использование множеств для подсчета уникальных просмотров страниц или отслеживания онлайн-пользователей.
* Паттерн Pub/Sub (Издатель/Подписчик): механизм обмена сообщениями в реальном времени. Как один сервис может "крикнуть" в канал, а пять других сервисов мгновенно это услышат, не опрашивая базу данных.
## Практика:
* Сохрани данные о корзине покупок пользователя, используя команду HSET (в Python метод hset). Обнови только количество одного товара, не перезаписывая всю корзину.
* Создай простую систему лайков: используй команду SADD (Redis Sets), чтобы добавлять ID пользователей, лайкнувших статью. Проверь количество лайков с помощью SCARD.
* Напиши два небольших Python-скрипта. Первый (subscriber.py) будет бесконечно слушать канал notifications через redis.pubsub(). Второй (publisher.py) будет отправлять туда текстовые сообщения. Запусти их в разных окнах терминала и посмотри на результат.

## Конспект изученных материалов
### 1. Хэши: точечное обновление данных
* **Проблема JSON-строки при обновлениях:** Если весь пользователб храниться как одна огромная JSON-строка ({"name": "David", "age": 16, "balance": 1000, "bio": "..."}), для изменения баланса придется сделать следующее:
    1. Выгрузить всю строку из Redis
    2. Десериализовать JSON в словарь Python
    3. Изменить значение balance
    4. Сериализовать словарь обратно в огромную JSON-строку.
    5. Отправить ее обратно в Redis
* Это создает сильную нагрузку на сеть, требует ресурсов процессора на парсинг JSON и, порождает состояние гонки (Race Condition). 
* **Решение: Структура Hash (Хэш):** Redis Hash - это словарь внутри словаря (хэш-таблица). Ключ в Redis указывает не на строку, а на набор полей и их значений.
* **Команды:**
    * *HSET key field value* - установить значение конкретного поля.
    * *HGET key field* - получить значение одного поля.
    * *HGETALL key* - получить все поля и значения.
    * *HINCRBY key field increment* - атомарно увеличить числовое значение поля (спасает от состояний гонки!).
### 2. Списки для очередей
* **Своими словами:** Redis Lists - это классические двусвязные списки из строк В них можно добавлять элементы в начало списка или в конец. Используя их можно сделать очень быстрые очереди задач по принципу FIFO
* **Команды:**
    * *LPUSH key value* - положить элемент слева (начало списка).
    * *RPOP key* - забрать и удалить элемент справа (конец списка).
    * *BRPOP key timeout* - Блокирующий RPOP. Скрипт "засыпает" и ждет, пока в списке не появится элемент (чтобы не крутить бесконечный цикл while True вхолостую).
### 3. Множества для уникальности
* **Redis Sets** - это неупорядоченные коллекции уникальных строк. В них не может быть дубликатов. Под капотом они реализованы как хеш-таблицы, поэтому проверка "есть ли такой элемент в множестве" (SISMEMBER) занимает $O(1)$ - то есть мгновенно, независимо от размера множества
* **Команды:**
    * *SADD key member* - добавить элемент (дубликаты игнорируются).
    * *SCARD key* - узнать размер множества (количество элементов).
    * *SISMEMBER key member* - проверить, есть ли элемент.
    * *SMEMBERS key* - получить все элементы.
### 4. Паттерн Pub/Sub (Publisher/Subscriber)
* В Pub/Sub данные вообще не сохраняются в базу. Аналогия этому паттерну радиостанция:
    * **Издатель (Publisher)** - это диджей на радио. Он вещает музыку в определенный канал (канал 101.5 FM). Ему неважно, слушает ли его кто-то.
    * **Подписчики (Subscribers)** - это радиоприемники. Если радиоприемник включен на волне 101.5 FM, он мгновенно услышит звук. Если приемник был выключен в момент передачи - он навсегда пропустил сообщение (история не сохраняется).
* **Зачем это нужно в микросервисах:**
    Представьте, что у вас есть микросервис "Уведомления", микросервис "Аналитика" и сервис "Кэширование". Когда пользователь покупает товар, основное API "кричит" в канал order_events: "Куплен товар X!". Все три сервиса, подписанные на этот канал, мгновенно получают эту строчку и начинают делать свою работу
* **Команды:**
    * *PUBLISH channel message* - отправить сообщение.
    * *SUBSCRIBE channel* - подписаться на канал(ы).
