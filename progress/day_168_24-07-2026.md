# День 168 (24.07.2026): Оптимизация Dockerfile и слои (Layers)
## Теория:
* Концепция слоев: каждая команда в Dockerfile (FROM, COPY, RUN) создает новый слой (layer). Слои кэшируются на жестком диске.
* Понимание кэша: почему порядок команд критически важен. Если изменился один файл, все инструкции RUN ниже команды COPY будут выполняться заново (что сильно замедляет сборку).
* Игнорирование мусора: зачем нужен файл .dockerignore (аналог .gitignore) и почему не стоит копировать локальные виртуальные окружения (venv) и папку .git внутрь образа.
* Легковесные образы: разница между полными образами и образами на базе Alpine Linux (например, python:3.10-alpine), которые весят в 10 раз меньше.
## Практика:
* Создай файл .dockerignore и добавь туда папки или файлы, которые не должны попасть в образ (например, README.md или .git).
* Измени базовый образ в твоем Dockerfile на версию -alpine (например, python:3.10-alpine).
* Собери образ заново с новым тегом: docker build -t my-app-alpine .
* Проверь размер образов командой docker images и сравни вес первой (стандартной) версии и версии Alpine.
* Измени код в app.py, запусти сборку снова и понаблюдай в консоли за тем, как Docker использует кэш (надпись CACHED) для верхних слоев.

## Конспект изученных материалов
### 1. Концепция слоев и кэширование
* **Docker-образ** это как слоеный пирог. Каждая значимая команда в Dockerfile добвляет в этот пирог новый слой поверх предыдещуго. 
* **Особенности слоев:**
    * Слои неизменяемы: Как тоько слой создан он фиксируется, если изменяется хотя бы один файл, Docker создаёт новый слой
    * Переиспользование (Кэширование): Docker сохраняет каждый слой на жесткой дике. Если при следующей сборке инструкция не изменилась (и файлы, к которым она обращается, остались теми же), Docker не будет выполнять её заново. Он просто возьмёт готовый слой из кэша
* Это сделано для того чтобы сборка происходила мгновенно. Но чтобы это работало, нужно правильно выстроить порядок команд.
### 2. Понимание кэша: почему порядок команд критически важен
* Правило Docker номер один: **если изменился один слой, все последующие слои (ниже него) будут собраны заново (кэш не используется).
* В Python-проектах самая долгая операция - это установка зависимостей (Уж с моим интернетом 100 KB/S это точно￣へ￣) *pip install*. Если ты напишешь Dockerfile неправильно, ты будешь ждать эту установку при каждом изменении хотя бы одной строчки кода.
___
* **Как делать не навдо:**
    * FROM python:3.13-slim
    * WORKDIR /app
    * COPY . . 
    * RUN pip install -r requirements.txt
    * CMD ["python", "app.py"]
* **Почему это плохо:** Если ты просто поменяешь опечатку в app.py, команда *COPY ..* заметит изменения. Docker скажет: "Ага, файлы изменились, слой копирования обновлен. Значит, все слои ниже идут в мусорку!". И он заново запустит *RUN pip install*, скачивая всё из интернета.
___
* **Как делать ПРАВИЛЬНО:** Нужно отделить редко изменяемые файлы (список зависимостей) от часто изменяемых (код приложения)
    * FROM python:3.11-slim
    * WORKDIR /app
    * COPY requirements.txt .
    * RUN pip install -r requirements.txt
    * COPY . .
    * CMD ["python", "app.py"]
* **Почему это хорошо:** Теперь, изменить код в app.py, Docker дойдет до Шага 1 и увидит что requirements.txt не менялся. Он возьмет слой установки зависимостей (Шаг 2) из кэша. Кэш сломается только на Шаге 3, а само копирование кода занимает доли секунды.
### 3. Игнорирование мусора
* **Своими словами:** Когда запускается *docker build .* он берет все папки и файлы из директории и передаёт их своему демону. А там могут быть ненужные файлы по типу: venv (виртуальное окружение из Windows не будет работать на Linux), и из-за других файлов сборка замедлится. И поэтому создаётся файл **.dockerignore** он работает точно также, как и .gitignore, и синтаксис добавления игнорируемых файлов такой же. И теперь команда *COPY . .* заберет только нужный исходный код проигнорировав этот мусор.
### 4. Легковесные образы
* **Разница между образами:**
    * **python:3.11 (Full)**: Размер огромный. Имеет полную версию на базе Debian. Включает кучу системных утилит (gcc, make, curl и т.д.). Почти никогда в продакшене не используется из-за своего веса. Плдходит для отладки и тестов.
    * **python:3.11-slim**: Размер до 120 мб. Уразанный Debian. Удалены тяжелые библиотеки и компиляторы, оставлены только самое необходимое для запуска Python. Золотой стандарт, практически всегда стоит выбирать этот вариант для Python-проектов.
    * **python:3.11-alpine**: Размер до 50 мб. Построен на Alpine Linux, и это максимально крошечный образ. Плохо для Python
* Размер базового образа напрямую влияет на размер финального контейнера. Несмотря на то, что Alpine весит меньше всего, он использует библиотеку musl вместо стандартной glibc. Многие популярные Python-пакеты (pandas, numpy, cryptography, psycopg2) распространяются в виде готовых колес (wheels), скомпилированных под glibc. На Alpine они не установятся напрямую - Docker придется скачивать компилятор С и собирать их из исходников, что может занять 20 минут (У меня целую вечность *из-за скорости интернета) и увеличить итоговый размер образа так, что он станет больше чес slim.
