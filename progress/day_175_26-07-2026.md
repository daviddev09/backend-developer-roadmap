# День 175 (26.07.2026): Защита веток (Branch Protection) и блокировка слияний
## Теория:
* Правила защиты веток (Branch Protection Rules): встроенный механизм GitHub для защиты важных веток (например, main или production) от случайных действий.
* Запрет на прямой пуш: почему профессионалы никогда не делают git push origin main, а используют исключительно Pull Requests.
* Требование успешных проверок (Require status checks to pass): как заставить GitHub блокировать кнопку "Merge pull request", пока workflow с тестами из Дня 173 горит красным.
* Код-ревью: настройка обязательного подтверждения PR от других разработчиков перед слиянием.
## Практика:
* В настройках репозитория на GitHub перейди в раздел "Branches" и создай правило (Branch protection rule) для ветки main.
* Поставь галочку "Require a pull request before merging" (запрет прямого пуша).
* Поставь галочку "Require status checks to pass before merging" и выбери в списке свой workflow с тестами.
* Попробуй сделать локальный коммит в ветку main и отправить его через git push origin main — ты должен получить отказ от сервера (ошибка доступа).
* Создай ветку, открой PR со сломанными тестами и убедись, что кнопка "Merge" заблокирована серым цветом и GitHub не дает тебе слить сломанный код.

## Конспект изученных материалов
### 1. Правила защиты веток
* **Своими словами:** Это механизм защиты веток предоставляемый GitHub. В нём можно тонко настроить защиту для конкретной ветки. В основном защищают ветку main ведь она всегда готовится к деплойу.
* **Где его найти:**
    1. В репозитории нужно зайти во вкладку "Settings"
    2. Найти в этой вкладке раздел "Branches"
    3. Нажать кнопку "Add branch protection rule"
    4. В поле "Branch name pattern" ввести имя ветки которую хотите защитить, после этого настроить механизмы защиты
### 2. Запрет на прямой пуш
* **Своими словами:** если делать прямой пуш в ветку main, то в этом случае обходятся проверки линтеров, тесты и т.п. Да, можно и для пуша в main настроить CI/CD но какой толк автоматических тестов после того как коммиты слиты с main? Никакой. И поэтому в настройках защиты нужно добавить механизм защиты которая будет запрещать делать прямые пуши в ветку main, обходя Pull Request. 
* **Как это сделать:**
    * В настройках поставить галочку напротив "Require a pull request before merging" (Требовать Pull Request перед слиянием)
    * По умолчанию эта настройка будет запрещать прямые пуши только обычным разработчикам а вот владельцам или администраторам запрета не ставиться, и когда они делают прямой пуш в консоли приходит только предупреждение о том что в эту ветку нельзя делать прямой пуш, но, их коммиты всё равно сливаются.
    * Чтобы запретить ВСЕМ прямой пуш нужно прокрутить вниз и там поставить галочку напротив "Do not allow bypassing the above settings"
### 3. Требование успешных проверок
* **Своими словами:** В тех же настройках можно задать защиту от сломанных тестов, то есть, если при Pull Request хоть один из тестов падает и тесты возвращают 1 вместо нуля, кнопка "Merge Pull Request" становиться серой и блокируется. Это делается для того чтобы защитить проект от человеческого фактора. Ведь кто-то может просто пропустить это и в main попадёт сломанный код. Туда можно добавить не только один но очень много количеств тестов, например: pytest, ruff, flake8 и т.п.
* **Как это сделать:**
    * В настройках поставить галочку напротив кнопки "Require status checks to pass before merging"
    * Затем в поисковике ниже написать имя своего **job** из файла конфигурации .yml и тест туда сам добавиться
### 4. Код-ревью
* **Своими словами:** даже если все проверки кода загорятся зелёными это не всегда значит что код написан правильно, ведь pytest или flake8 не проверяют логику кода. И здесь нужен Код-ревью. Code Review это когда один написал код и говорит коллеге: "Я написал код сделай код ревью", и коллега проверяет код если всё отлично, он нажимает "Approve" а если нет он пишет замечания где, что нужно исправить. И тот разработчик берёт исправляет логику и опять просит код ревью и если всё ок, тогда можно слиять Pull Request в main.
* **Как это сделать:**
    * Внутри блока "Require a pull request before merging" отметить галочкой "Require approvals". Там можно выбрать количество необходимых код-ревью для слияния.
