# День 200 (02.08.2026): Проблема N+1 и оптимизация запросов в ORM
## Теория:
* Что такое проблема N+1: самый частый и коварный баг производительности в любом веб-фреймворке (Django, SQLAlchemy). Как ORM незаметно делает 101 запрос в базу данных вместо 1-го при попытке вывести список пользователей и их посты.
* Ленивая загрузка (Lazy Loading) против Жадной (Eager Loading): как ORM по умолчанию подтягивает связанные данные (отношения ForeignKey) и почему это тормозит API.
* Решение проблемы в SQLAlchemy: использование методов joinedload() (для связей One-to-One/Many-to-One через SQL JOIN) и selectinload() (для One-to-Many).
* Решение в Django ORM (если используешь его): методы select_related и prefetch_related.

## Конспект изученных материалов
### 1. Проблема N+1 запросов
* **Своими словами:** Проблема N+1 запросов возникает когда при получении данных из БД делается LazyLoad. Это значит что если мы хотим получить 100 пользователей, ORM делает 1 запрос чтобы получить всех пользователей. А когда мы сделаем print(user.posts) ORM начинает выполнять столько запросов сколько было пользователей. Если пользователей 100, то 100+1 это количество общих запросов. И в каждом из ста запросов он будет вставлять id пользователя и запрашивать посты: *SELECT * FROM posts WHERE user_id = N* 
### 2. Lazy Loading против Eager Loading
* **Lazy Loading** делает 1 запрос к БД и получает 100 пользователей, а потом генерирует запрос подставляя ID этих пользователей чтобы получить связанные с ними данные, получается 1 запрос чтобы получить всех 100 пользователей, ещё 100 запросов чтобы получить данные каждого из них
* **Eager Loading** делает 1 запрос к БД и получает 100 пользователей, генерирует один большой SQL в которые ставит ID всех пользователей чтобы получить связанные данные. Это всего 2 запроса.
### 3. Решение проблемы в SQLAlchemy
* **Своими словами:**
    * **Joinedload:** SQLAlchemy когда загружает данные делает один большой Left Join чтобы получить связи. Применяется для связей Многие к одному и Один к одному, когда нужно получить 100 постов и их владельца
    * **Selectinload:** Делает ровно два запроса: **1)** Получает всех пользователей, **2)** Берёт id полученных пользователей и делает запрос к дочерней таблице: *SELECT * FROM posts WHERE user_id IN(1, 2, 3, ...)*. Это абсолютный золотой стандарт для связей Один ко многим и Многие к многим
