# День 183: Деплой веб-приложения и связывание сервисов
## Теория:
* Способы доставки кода в PaaS: нативный билд (когда сервер сам устанавливает Python и делает pip install) против деплоя готового Docker-образа (через Dockerfile).
* Команды сборки (Build Command) и команды запуска (Start Command): как объяснить облачному провайдеру, что именно нужно сделать для старта твоего кода.
* Управление конфигурацией в облаке: панель Environment Variables (переменных окружения). Как перенести локальный файл .env в облачный интерфейс.
* Бесшовное связывание: как передать внутренний адрес базы данных (Internal URL), созданной во вчерашнем дне, в переменную окружения веб-сервиса.
## Практика:
* В панели управления облаком (Render/Fly.io) создай новый "Web Service" и подключи свой репозиторий GitHub.
* Если используешь нативный деплой, укажи команду сборки (например, pip install -r requirements.txt) и команду запуска (например, uvicorn main:app --host 0.0.0.0 --port $PORT). Если используешь Docker, просто укажи пть к Dockerfile.
* В разделе Environment Variables добавь все необходимые секреты из твоего локального .env файла.
* В качестве переменной DATABASE_URL (или как она у тебя называется) укажи Internal URL твоей облачной базы данных.
* Запусти ручной деплой (Manual Deploy) и дождись, пока провайдер выдаст тебе публичный URL-адрес (например, httрs://my-app.onrender.com).
* Открой этот адрес в браузере и убедись, что приложение работает и успешно связывается с БД.

## Конспект изученных материалов
### 1. Способы доставки кода в PaaS
* **Нативный билд:** сервер сам скачивает твой код, находит requirements.txt и выполняет pip install.
    * **Плюсы:** Максимально удобно для новичков. Не нужно знать синтаксис Docker
    * **Минусы:** Зависимость от окружения провайдера. Если коду нужна специфическая системная библиотека например для обработки видео, её может не оказаться на сервере.
* **Деплой через Docker:** Сервер берёт Dockerfile и собирает его точно также, как это делалось бы локально, и запускает контейнер.
    * **Плюсы:** Абсолютная предсказуемость. Если образ собрался и работал на ноутбуке, он на 100% будет работать в облаке.
    * **Минусы:** Требует базового понимания слоев Docker и правильного написания Dockerfile
### 2. Команды сборки
* **Build Command:** Эта команда выполняется один раз в изолированной среде во время выкатывания новой версии.
    * **Пример использования:** Установка зависимостей, компиляция стилей, применение миграций базы данных.
    * **Пример команды (для нативного сбора):** *pip install -r requirements.txt && alembic upgrade head*
* **Start Command:** Эта команда запускает главный процесс приложения. Она должна работать постоянно.
    * **Пример команды:** *uvicorn main:app --host 0.0.0.0 --port $PORT*
### 3. Управление конфигурацией в облаке.
* **Своими словами:** Никогда нельзя хардкодить данные переменных окружения в коде, нельзя собирать в Dockerfile и не дать попасть им в публичный репозиторий. И поэтому нужно при создании PaaS перейти в раздел Environments, нажать Add Environment, в поле name добавить название переменной, а в поле value добавить значение. И когда платформа будет запускать приложение, он добавит эти данные в переменные окружения ОС контейнера и прилпжения могут получать его из os.getenv или же из BaseSettings.
### 4. Бесшовное связывание.
* Бесшовное связывание это когда берёшь Internal URL своего Managed Database, и связываешь его со своим приложением. 
* **Как делается:**
    * Копируешь Internal URL из настроек своего облачной БД
    * Добавляешь его в панели Environment Variables своего веб-сервиса под ключом DATABASE_URL (если твоё приложение ожидает такое название)
