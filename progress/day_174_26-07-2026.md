# День 174 (26.07.2026): Секреты (Secrets) и переменные окружения
## Теория:
* Проблема безопасности: почему категорически нельзя хардкодить пароли от баз данных, API-ключи и токены прямо в файлах .yml.
* GitHub Repository Secrets: безопасное зашифрованное хранилище переменных в настройках твоего репозитория.
* Контекст ${{ secrets.MY_SECRET }}: как безопасно извлекать секреты во время выполнения Workflow.
* Разница между env (переменными окружения на уровне шага или джоба) и secrets.
* Как GitHub маскирует (скрывает звездочками ***) секреты в публичных логах раннера, чтобы их нельзя было подсмотреть.
## Практика:
* Зайди в настройки своего репозитория на GitHub (Settings -> Secrets and variables -> Actions).
* Создай новый секрет с названием API_KEY и значением super_secret_token_123.
* В своем файле tests.yml добавь шаг, который пытается вывести этот секрет в консоль через run: echo "My token is ${{ secrets.API_KEY }}".
* Запусти action и посмотри в логи: убедись, что вместо значения вывелись звездочки.
* Передай этот секрет в качестве переменной окружения в шаг тестирования (используя блок env:), чтобы твои тесты могли использовать его во время работы.

## Конспект изученных материалов
### 1. Проблема безопасности: Почему нельзя хардкодить секретные данные
* **Своими словами:** харкодить, то есть писать секретные данные (пароли БД, АПИ ключи и т.п.) в файлах таких как .yml которые попадут в репозиторий это огромная дыра в безопасности. Потому что если репозиторий открытый, то боты за несколько секунд найдут эти данные, а любой пользователь Гитхаб может смотреть их в репозитории, и даже если это приватный репозиторий то не всем в команде нужно знать секретные данные от сервера и т.п. 
### 2. GitHub Repository Secrets
* **Своими словами:** GitHub предоставляет очень полезную возможность хранить свои секретные данные в настройках репозитория. Оно находится в: repository -> settings -> secrets and environments. Это хранилище при сохранении берёт название секрета и значение, а потом шифрует значение криптографическим алгоритмом прямо на месте и даже владелец не сможет прочитать эти секретные данные, их можно удалить или заменить на новый но, никак не прочитать. Это даёт хорошую конфиденциальность и не придётся писать секретные данные в файлах которые будут лететь в публичный репозиторий.
### 3. Контекст ${{ secrets.MY_SECRET}}
* **Своими словами:** Чтобы использовать зашифрованные секретные данные из настроек репозитория используется этот синтаксис: *${{ secrets.MY_SECRET }}*. Оно как бы говорит GitHub: Положи сюда значение секрета под названием: MY_SECRET. Это позволяет безопасно извлекать секретные данные из хранилища секретов. Никто ничего не видит. Однако GitHub Actions не подставляет эти значения в код, он подставляет их на уровне ОС, а python скрипты сами должны получить его во время выполнения тестов: *os.getenv('JWT_SECRET_KEY')*
### 4. Разница между env и secrets
* **Своими словами:** Разница между ними в том что как данные в них хранятся. Например, данные в переменных окружения хранятся в открытом виде: **TEST_DB_USER=test_user**, **DEBUG=True** и т.д. А в секретах данные хранятся в зашифрованном виде, туда входят: Пароли, API ключи, ssh private ключи, имена пользователей и т.п. 
### 5. Как GitHub маскирует секреты в логах
* **Своими словами:** Если кто-то решит похитрить чтобы увидеть данные зашифрованных секретов, он может в workflow файле прописать вот такую строку: *run: echo 'My secret is ${{ secrets.MY_SECRET }}. Допустим он так и написал и хочет увидеть в логах Actions его значение, но GitHub маскирует значение этой строки под звёздочками ('**'). Например значение секрета равно 123, и если GitHub Actions встретит в логах такое значение где бы то ни было если оно соответствует значению одного секрета из настроек то он замаскирует их под звёздочками. Поэтому для секретов нужно использовать длинные надёжные значения которые очень очень редко встречаются. А лучше и вообще не пытаться вывести секретные данные в логах.
