# День 171 (25.07.2026): Введение в CI/CD и основы GitHub Actions
## Теория:
* Концепция CI (Непрерывная интеграция): зачем нужно автоматически проверять код при каждом пуше. Как это предотвращает попадание сломанного кода в главную ветку.
* Концепция CD (Непрерывная доставка/развертывание): автоматическая сборка и отправка проверенного кода на сервер.
* Что такое GitHub Actions: встроенный в GitHub инструмент для автоматизации любых процессов (workflows) при наступлении определенных событий в репозитории.
* Базовая терминология Actions:
    * Workflow (рабочий процесс): автоматизированный процесс (например, "Тестирование кода"), состоящий из одного или нескольких Job.
    * Event (событие): триггер, запускающий workflow (например, push или pull_request).
    * Runner (раннер): сервер (виртуальная машина), на котором выполняется твой процесс (чаще всего используются бесплатные серверы Ubuntu от GitHub).
* Где живут настройки: структура директории .github/workflows/ и обязательный формат файлов .yml.
## Практика:
* В корне своего проекта создай директорию .github/workflows/.
* Внутри создай файл first_action.yml.
* Напиши простейший workflow, который реагирует на push, запускается на ubuntu-latest и выполняет команду терминала echo "Hello, GitHub Actions!".
* Сделай коммит, отправь его на GitHub и перейди во вкладку "Actions" в репозитории, чтобы увидеть, как отработал твой первый раннер.

## Конспект изученных материалов
### 1. Концепция CI
* **Continuous Integration (CI)** - это практика разработки, при которой код регулярно сливается в общуй ветку репозитория. Когда над проектом работают даже один программист, есть риск сломать то что уже работало.
* **Как CI предотвращает попадание сломанного кода в main:
    1. Делается push или создается pull_request в главную ветку.
    2. Вместо того, чтобы сразу слить код, GitHub запускает CI-пайплайн (скрипт проверок).
    3. В облаке поднимается чистый сервер. Он скачивает новый код, устанавливает зависимости, подключает тестовую БД и запускает тесты (например, pytest)
    4. Если хотя бы один тест падает, процесс загорается красным крестиком. Код блокируется и не попадает в main.
### 2. Концепция CD
* **CD** состоит из двух родственных понятий:
    * **Continuous Delivery**: Код проходит CI, и система автоматически собирает например, готовый Docker образ FastAPI приложения. Этот образ готовится к отпраке на сервер, но само обновление на сервере происходит по нажатию кнопки человеком.
    * **Continuous Deployment**: Полностью автоматизированный процесс. Как только тесты пройдены, система собирает Docker-образ, но и сама подключается к рабочему серверу по SSH, останавливает старый контейнер и запускает новый.
### 3. GitHub Actions
* **GitHub Actions** это мощный инструмент предоставляемый самим GitHub. Он в репозитории написан как: Actions. GitHub Actions бесплатно даёт пользователям сервер для автоматизиции проверок. Когда делается push в ветку main он может запустить ВМ, внутри установить ОС и провести тесты и всё это на удалённых серверах.
### 4. Базовая терминология Actions
* **Event**: Событие которое всё запускает. Например: Кто-то сделал push, наступило 12:00 по расписанию и т.п.
* **Workflow**: Это один пайплайн, отвечающий за задачу. Например, "Запуск тестов" или "Деплой на сервер".
* **Job**: Внутри workflow может быть несколько Job. Они по умолчанию выполняются параллельно на разных серверах. Например, одна Job тестирует код на Python 3.10, а другая параллельно на Python 3.11
* **Runner**: Тот самый сервер, на котором выполняется Job. GitHub бесплатно предоставляет виртуальные машины. 
* **Step**: Каждая Job состоит из шагов. Шаги выполняются строго по очереди. Это может быть либо консольная команда(например *pip install*), либо готовый Action.
* **Action**: Готовый переиспользуемый кусок кода от сообщества. Например, не нужно писать с нуля скрипт установки Python, можно взять готовый Action *actions/setup-python@v4*
### 5. Где живут настройки
* Чтобы GitHub понял, что вы хотите запустить автоматизацию, вам нужно положить конфиграционный файл в строную структуру папок в корне проекта: *.github/workflows/название_файла.yml*. Файлы пишутся на языке разметки YAML. В нем нет фигурных скобок, всё строится на отступах.
