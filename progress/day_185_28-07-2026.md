# День 185 (28.07.2026): Пост-деплой тестирование и Health Checks (Проверки работоспособности)
## Теория:
* Почему "зеленые" тесты в GitHub Actions (CI) не гарантируют, что приложение реально запустится на боевом сервере (ошибки конфигурации, отвалившаяся БД, нехватка памяти).
* Концепция Smoke Testing (дымовое тестирование): быстрая проверка базового функционала на "живом" сервере после деплоя.
* Что такое Health Check (эндпоинт проверки здоровья): специальный маршрут (обычно /health или /ping), который нужен облачному балансировщику нагрузки (Load Balancer), чтобы понять, живо твое приложение или "зависло".
* Основы внешнего мониторинга: зачем нужны сервисы, которые "пингуют" твой сайт каждую минуту и шлют уведомления в Telegram при его падении.
## Практика:
* Напиши в коде своего приложения простейший эндпоинт /health, который всегда возвращает HTTP статус 200 и JSON {"status": "ok", "db_connected": true}.
* Добавь в этот эндпоинт легкий запрос к базе данных (например, SELECT 1), чтобы маршрут падал с ошибкой 500, если связь с БД оборвалась.
* Запушь этот код, дождись автоматического деплоя (из Дня 184).
* Настрой в облачном провайдере "Health Check Path", указав путь /health (система начнет сама проверять его каждые несколько секунд).
* Зарегистрируйся в бесплатном сервисе мониторинга (например, UptimeRobot или Better Stack), добавь туда свой публичный URL и настрой получение писем на почту в случае падения сервера.

## Конспект изученных материалов
### 1. Почему зелёные тесты не гарантируют успешный запуск приложени
* **Своими словами:** успешные тесты в GitHub Actions (CI) проводятся в на чистой ВМ где все компоненты приложения работают в единой системе и вся конфигурация вместе. Но когда приложение деплоиться (CD) на боевой сервер, оно может не запуститься по причинам: Локально где есть 8 ГБ оперативной памяти запускается но на сервере с 1 ГБ рам он ляжет из-за нехватки RAM. Если забыли в Environments добавит пароли или ссылки. Если БД которая работает на другом сервере легла и не отвечает и т.д.
### 2. Концепция Smoke Testing
* **Своими словами:** сам термин проверки дымом пришёл из сантехники где мастер пускал дым в водопровод и если дым ниоткуда не выходил значит и вода тоже не будет выходить - всё исправно. В программировании эта концепция означает быстрое тестирование работоспособность приложения. Smoke Testing не делает запросы где нужно вытащить тысячи пользователей или пройтись по всем юнит тестам. Это метод проверки где проверяется:
    * Можно ли открыть главную страницу сайта?
    * Можно ли зарегистрироваться?
    * ...
### 3. Что такое Health Check
* **Своими словами:** это эндпоинт проверки работы здоровья приложения. Это специальный маршрут обычно */health* который нужен исключительно балансировщику нагрузки сервера. Он каждые несколько секунд отпарвляет запрос на этот маршрут и проверяет жив ли контейнер, если он не отвечает значит контейнер завис, и балансировщику нужно перенаправить запросы пользователей на другой контейнер.
### 4. Основы внешнего мониторинга
* **Своими словами:** Внешний мониторинг нужен для проверки твоего сервиса на постоянной основе и уведомления если вдруг сервис упадёт. Внешний мониторинг это бот, программа которая например каждые 5 минут отправляет запрос например на эндпоинт /health и если оно не отвечает сервис мониторинга отправляет тебе сообщение через телеграм бота или по почте. Такая система должна быть вне сервера приложения потому что, если они будут на одном физическом сервере и тот сервер ляжет, то и система мониторинга также ляжет и не сможет уведомлять.
