# День 184 (28.07.2026): Непрерывное развертывание (Continuous Deployment) и Логирование
## Теория:
* Концепция Continuous Deployment (CD): как сделать так, чтобы сервер автоматически забирал новый код сразу после успешного прохождения тестов на GitHub.
* Механизм Webhooks: как GitHub уведомляет Render/Fly.io о появлении новых коммитов в ветке main.
* Понятие Zero-Downtime Deployment (деплой без простоев): почему система сначала поднимает новую версию контейнера, дожидается её готовности и только потом выключает старую.
* Анализ продакшен-логов: разница между логами сборки (Build Logs — ошибки установки библиотек) и логами приложения (Application Logs — ошибки в самом коде при реальных запросах).
## Практика:
* В настройках твоего Web Service в облаке найди и активируй опцию "Auto-Deploy" (автоматический деплой при пуше в подключенную ветку).
* Открой свой локальный код, внеси небольшое, но заметное изменение (например, измени сообщение на главной странице API или добавь новый тестовый эндпоинт).
* Сделай коммит и отправь его в ветку main на GitHub (git push).
* Мгновенно открой дашборд облачного провайдера. Наблюдай за тем, как система сама обнаружила пуш, запустила процесс сборки (Build) и выкатила новую версию.
* Зайди во вкладку Logs в облаке и найди там логи старта твоего обновленного приложения.

## Конспект изученных материалов
### 1. Концепция Continuous Deployment
* **Continuous Deployment:** это автоматизация развёрьвания. Если все тесты в CI прошли успешно, система автоматически без участия человека отпарвляет новый код на боевой сервер.
### 2. Механизм Webhooks
* Webhook (Вебхук) - это механизм уведомления одного другим с помощью обычного HTTP POST-запроса, реагирующий на какое-то событие.
    * **Обычный API (Polling):** Render каждые 5 секунд спрашивал бы у GitHub: "Есть новые коммиты? А сейчас? А сейчас?". Это неэффективно и нагружает сеть.
    * **Webhook:** Render дает GitHub специальную секретную ссылку (URL). Render молчит, пока в GitHub не произойдет событие в push. В этот момент GitHub сам отправляет HTTP POST-запрос на эту ссылку.
### 3. Zero-Downtime Deployment
* **Paas платформы** используют стратегию развертывания Zero-Downtime Deployment (Деплой без простоев)
* **Пошаговый алгоритм Zer-Downtime Deployment:**
    1. Контейнер А (Старый / V1): Работает и обрабатывает текущий пользолвательский трафик.
    2. Сбока контейнера B (Новый / V2): Облачный провайдер параллельно скачивает новый код и собирает Docker-образ в изолированном окружении. Контейнер А в это время ничего не знает и продолжает работать.
    3. Запуск и Health Check: Облако запускает контейнер C и начинает опрашивать его эндпоинт проверки здоровья 
    4. Переключение трафика: Как только контейнер В ответил HTTP 200 OK, балансировщик нагрузки (Load Balancer) мгновенно перенаправляет поступающие запросы клиентов с Контейнера А на Контейнер В.
    5. Мягкое завершение: Контейнеру А отправляется сигнал SIGTERM. Он дорабатывает текущие (уже принятые) запросы и корректно выключается
### 4. Анализ продакшен-логов
* В PaaS логи делятся на два типа:
    * **Build logs**
    * **Application logs**
* **Build logs (Логи сборки):**
    * Это логи которые генерируются до того, как приложение начало работать. Они отражают процесс создания окружения (установка пакетов, сборка Dockerfile).
* **Apllication logs (Логи приложения)Ж**
    * Это логи которые генерируется во время работы приложения, когда оно уже запущено и обрабатывает реальные запросы пользователей. Они возникают в процессе жизни приложения.
