# День 201 (04.08.2026): Индексы в базе данных и SQL EXPLAIN
## Теория:
* Как работают индексы в реляционных БД: структура B-Tree (Б-дерево). Аналогия с оглавлением в книге, которое позволяет не читать все 500 страниц в поисках одного слова.
* Когда индексы нужны, а когда вредят: почему нужно индексировать столбцы, которые часто используются в WHERE, ORDER BY и JOIN. И почему нельзя вешать индексы на все подряд (замедление операций INSERT и UPDATE, рост размера БД).
* Анализ запросов с помощью EXPLAIN / EXPLAIN ANALYZE: как база данных сама решает, как ей искать данные (План выполнения запроса).
* Чтение плана выполнения: разница между Sequential Scan (полное сканирование таблицы - медленно) и Index Scan (поиск по индексу - быстро).
## Практика:
* Напиши скрипт, который генерирует таблицу employees и заполняет её 1 миллионом строк (с полями id, name, department, salary).
* Подключись к базе (через DBeaver/DataGrip или терминал) и выполни запрос EXPLAIN ANALYZE SELECT * FROM employees WHERE name = 'John Doe';. Посмотри на время выполнения и надпись Seq Scan.
* Создай индекс: CREATE INDEX idx_emp_name ON employees (name);.
* Снова выполни EXPLAIN ANALYZE для того же запроса. Убедись, что метод поиска изменился на Index Scan, а время выполнения сократилось с сотен миллисекунд до долей миллисекунды.

## Конспект изученных материалов
### 1. Индексы в РБД
* **Своими словами:** по умолчанию в Postgres используется индексы B-Tree (Balanced Tree). Индексы ускоряют чтение из таблицы. Например без индексов в таблице на миллион строк, в худшем случае поиск прошёлся бы по миллионам строк и взял только последний а остальные бы выбросил, но индексы B-Tree работа.т по алгоритму бинарного поиска, и в такой таблице в худшем случае поиск пройдётся всего через 20 шагов 
### 2. Когда индексы нужны, а когда вредят
* **Индексы** это не бесплатная магия. Это реальные структуры данных, которые хранятся на жестком диске рядом с основной таблицей.
* **Когда индексы нужны:**
    1. В условиях: если часто ищутчя пользователи по email, индекс на колонку email обязателен
    2. Для связей (Foreign Keys): колонки, по которым делается Join
    3. Для сортировки (Order By): Индекс B-Tree уже отсортирован. Если спросить базу что-то отсортировать, при наличии индекса ей не придется тратить процессорное время на сортировку миллионов строк в памяти - она просто прочитает индекс с конца.
* **Когда индексы вредят:**
    1. Замедление записи (INSERT/UPDATE/DELETE)
    2. Расход места
    3. Колонки с низкой уникальностью: нет смысла вешать индекс на boolean-колонку. Если запрос вернет 50% таблицы, оптимизатор БД решит, что дешевле просто прочитать таблицу целиком
### 3. Анализ запросов: EXPLAIN и EXPLAIN ANALYZE
* Когда отправляется SQL-запрос, БД не выполняет его вслепую. Сначала работает планировщик. Он оценивает разные пути выполнения данных и выбирает самый "дешевый"
* **Чтобы узнать, что задумал планировщик, используют команду EXPLAIN:**
    * *EXPLAIN SELECT * FROM users WHERE email = 'daviddev@example.com';* База вернет предполагаемый план действий. Запрос при этом не выполняется. Это просто чертеж.
    * *EXPLAIN ANALYZE SELECT ...;* База реально выполнит запрос, замерит время и покажет как предполагаемый план, так и фактическое время выполнения в миллисекундах (ms). Это главный инструмент для дебага тормозящих эндпоинтов.
